# Shadow FTQ: 현재 구현 상태

> **설계 목표**: 논문 Section III-B (Constructing the TEA Thread at Fetch) 및 Section IV-D (TEA thread frontend)의
> TEA Fetch 메커니즘을 모델링.
> 논문에서는 128-entry Shadow FTQ + Block Cache 기반 basic block 조합 방식을 사용하지만,
> 현재 구현은 **방안 A (Dependency Chain Cache 직접 조회)** 를 채택하여 동등한 효과를 달성한다.

---

## 1. 논문의 Shadow FTQ 아키텍처

논문 Section III-B, IV-D에서 설명하는 TEA Fetch 메커니즘:

```
Branch Predictor (decoupled BP)
    │
    ├─→ Main Thread Fetch Queue (FTQ)  ← main thread가 I-cache에서 fetch
    │
    └─→ Shadow Fetch Queue (128-entry) ← TEA thread가 Block Cache에서 fetch
                │
                ▼
         Block Cache (512 entries + 256 tag store)
           ├─ basic block 단위로 저장
           ├─ bitmask로 dependency chain ops 표시
           └─ 여러 basic block segments를 조합하여 전체 H2P chain 구성
                │
                ▼
         TEA Rename Stage (8-wide, Shadow RAT)
```

> "Fetch addresses generated by the branch predictor are sent to both the Block Cache and the
> I-cache. The main thread consumes fetch addresses at a lower rate compared to the TEA thread.
> To account for this mismatch, the Fetch Queue for the TEA thread is much larger than a
> traditional Fetch Queue (can hold up to 128 fetch addresses)." — 논문 Section IV-D

**핵심 동작**:
1. Decoupled BP가 fetch address 생성 → FTQ와 Shadow FTQ 양쪽에 삽입
2. TEA thread가 Shadow FTQ에서 address를 꺼내 Block Cache entry 조회
3. Block Cache에서 basic block별 bitmask로 dependency chain ops만 추출
4. 여러 basic block segments를 순서대로 조합하여 전체 chain 구성
5. TEA의 fetch 속도 > Main thread fetch 속도 (BP throughput > frontend bandwidth)

**논문 Table II 수치**:
| 구조 | 크기 |
|------|------|
| Shadow FTQ | 128-entry FIFO |
| Block Cache | 512 entries + 256 zero-tag entries |
| TEA Fetch/Rename | 8-wide, 9-cycle frontend latency |

## 2. 현재 구현: 방안 A (Dependency Chain Cache 직접 조회) — ✅

현재 TEA Fetch는 Shadow FTQ를 **사용하지 않는다**.
`dependency_chain_caches`에 pre-aggregated된 전체 H2P chain을 H2P PC로 직접 조회하여 fetch.

```
HBT 감지: H2P branch at Fetch (bp.c:878)
    │
    ▼
trigger_tea_thread(proc_id, h2p_pc, h2p_op_num, h2p_op)
  (tea_thread.c:99)
    │
    ├─ get_dependency_chain(proc_id, h2p_pc) — chain 존재 확인
    │   (dependency_chain_cache.c:266)
    │
    ├─ shadow_rat_snapshot(proc_id) — Main RAT → Shadow RAT 복사
    │   (tea_rename.c:176)
    │
    └─ reset_tea_fetch_stage(proc_id) — fetch state 초기화
        (tea_fetch_stage.c:87)
    │
    ▼
매 cycle: update_tea_fetch_stage(proc_id)
  (tea_fetch_stage.c:113, cmp_model.c:287에서 호출)
    │
    ├─ active_chain이 NULL이면 get_dependency_chain()으로 조회
    │   (tea_fetch_stage.c:132-143)
    │
    ├─ chain[current_chain_idx]에서 순차적으로 TEA_FETCH_WIDTH개씩 fetch
    │   (tea_fetch_stage.c:157-178)
    │
    └─ current_chain_idx >= total_chain_length이면 fetch_complete = TRUE
        (tea_fetch_stage.c:181-183)
```

### 2.1 Dependency Chain Cache 구조

`dependency_chain_caches` (`dependency_chain_cache.h:31-39`)는 H2P PC로 인덱싱되며,
Backward Dataflow Walk가 생성한 전체 dependency chain을 하나의 엔트리에 저장:

```c
typedef struct Dependency_Chain_Cache_Entry_struct {
  Flag          is_valid;
  Addr          h2p_branch_pc;        // H2P 분기의 PC (= 조회 키)
  Counter       h2p_branch_op_num;
  uns           chain_length;          // 체인 내 op 수
  Op            chain[MAX_CHAIN_LENGTH]; // 최대 64개 ops
  uint64_t      dependency_mask;
  uns           total_ops_in_block;
} Dependency_Chain_Cache_Entry;
```

조회 함수 (`dependency_chain_cache.c:266-274`):
```c
Dependency_Chain_Cache_Entry* get_dependency_chain(uns proc_id, Addr pc) {
    int entry_index = pc % DEPENDENCY_CHAIN_CACHE_SIZE;
    Dependency_Chain_Cache_Entry* entry = &dependency_chain_caches[proc_id][entry_index];
    if (entry->is_valid && entry->h2p_branch_pc == pc) {
        return entry;
    }
    return NULL;
}
```

### 2.2 TEA Fetch Stage 구조체 (`tea_fetch_stage.h:45-60`)

```c
typedef struct Tea_Fetch_Stage_struct {
  uns8 proc_id;
  Stage_Data sd;                              // 출력 (TEA Rename으로 전달)

  Dependency_Chain_Cache_Entry* active_chain; // 현재 fetch 중인 chain
  int current_chain_idx;                      // chain 내 현재 위치
  int total_chain_length;                     // chain 총 길이

  Flag fetch_complete;                        // 모든 ops fetch 완료 여부
  Counter ops_fetched_this_cycle;             // 현재 cycle fetch된 ops 수
} Tea_Fetch_Stage;
```

### 2.3 TEA Fetch → Rename → Dispatch 파이프라인

`cmp_model.c:284-289`의 per-cycle 루프에서 실행:

```c
/* TEA Thread update */
if (TEA_ENABLE && tea_is_active(proc_id)) {
  update_tea_rename_stage(proc_id, &tea_fetch_stages[proc_id]->sd);  // (1)
  update_tea_fetch_stage(proc_id);                                    // (2)
  update_tea_thread(proc_id);                                         // (3)
}
```

**호출 순서 (역순 파이프라인 업데이트)**:
1. `update_tea_rename_stage()` (`tea_rename.c:395`): 이전 cycle의 fetch 출력(`sd`)을 rename
   - Shadow RAT에서 src phys reg 읽기, TEA preg pool에서 dst 할당
   - Rename된 ops를 `rename->sd`에 저장 → `tea_dispatch_to_rs()`로 전달
2. `update_tea_fetch_stage()` (`tea_fetch_stage.c:113`): 이번 cycle의 fetch 수행
   - `active_chain`에서 `TEA_FETCH_WIDTH`개 ops를 `tea_create_op_from_cache()`로 생성
3. `update_tea_thread()` (`tea_thread.c:210`): 상태 전이 확인
   - `TEA_FETCHING` + `fetch_complete` → `TEA_EXECUTING`
   - `TEA_EXECUTING` + `tea_op_count == 0` → `terminate_tea_thread()`

### 2.4 TEA Op 생성 (`tea_create_op_from_cache()`, `tea_fetch_stage.c:189-237`)

```c
Op* tea_create_op_from_cache(uns proc_id, Op* cached_op, Flag is_h2p_branch) {
  Op* tea_op = alloc_op(proc_id);           // op pool에서 할당

  // 정적 정보 복사 (inst_info, table_info)
  tea_op->inst_info = cached_op->inst_info;
  tea_op->table_info = cached_op->table_info;

  // TEA 동적 정보 설정
  tea_op->thread_id = 1;                     // TEA 식별
  tea_op->op_num = tea->tea_op_counter++;    // 별도 번호 공간
  tea_op->fetch_cycle = cycle_count;
  tea_op->state = OS_FETCHED;

  // H2P branch: oracle_info/recovery_info를 trigger 시 저장된 Main H2P에서 복사
  if (is_h2p_branch) {
    tea_op->oracle_info = tea->h2p_oracle_info;
    tea_op->recovery_info = tea->h2p_recovery_info;
  }

  tea->tea_op_count++;
  return tea_op;
}
```

**H2P branch 판별**: chain의 마지막 op이 H2P branch (`tea_fetch_stage.c:163`):
```c
Flag is_h2p_branch = (tea_fetch->current_chain_idx == tea_fetch->total_chain_length - 1);
```

## 3. 방안 A vs 논문 방식 비교

| 측면 | 논문 (Shadow FTQ + Block Cache) | 방안 A (Dep Chain Cache 직접 조회) |
|------|-------------------------------|----------------------------------|
| **Fetch 소스** | Shadow FTQ → Block Cache (basic block 단위) | `dependency_chain_caches` (전체 chain 단위) |
| **Chain 조합** | 여러 basic block bitmask를 런타임에 조합 | BW Walk 시점에 이미 조합 완료 |
| **FTQ 의존성** | decoupled BP의 fetch address 스트림 필요 | FTQ 불필요 (H2P PC만으로 조회) |
| **중간 분기 처리** | BP가 중간 분기 방향 예측 → 다양한 control flow 커버 | BW Walk 시점의 control flow만 반영 |
| **복잡도** | 높음 (FTQ 공유/분리, Block Cache 조합 로직) | 낮음 (단일 캐시 조회) |
| **다중 H2P** | 각 H2P에 대해 FTQ address 소비 | 각 H2P에 대해 `get_dependency_chain()` 호출 |

### 3.1 기능적 동등성

방안 A의 `dependency_chain_caches`는 논문의 Block Cache + bitmask OR 조합의 **최종 결과물**을
BW Walk 시점에 미리 계산하여 저장한 것과 같다.

- `add_dependency_chain()` (`dependency_chain_cache.c:92-226`)이 BW Walk 완료 시 호출
- 이 함수는 SourceList 기반 backward walk → `is_data_dependent[]` 마킹 → chain 추출
- **동시에** Block Cache에도 basic block별 bitmask 저장 (line 170-225)

따라서 두 캐시가 병렬로 채워지지만, TEA Fetch는 `dependency_chain_caches`만 사용.

### 3.2 Block Cache의 현재 역할

`block_caches`와 `get_dependency_chain_block()` (`dependency_chain_cache.c:277-285`)은
현재 구현에서 TEA Fetch가 직접 조회하지 않는다. BW Walk이 채우지만 TEA Fetch는 dep cache만 사용.

**Hybrid Chain 계획 (작업 HC)**: dep cache chain을 Block Cache의 OR 누적 bitmask로부터
재구축하여, 다중 경로의 합집합 chain을 구성. 이를 통해 Block Cache가 간접적으로 TEA Fetch에
기여하게 됨. 상세: [`TEA_hybrid_chain_plan.md`](../TEA_implementation_plan/TEA_hybrid_chain_plan.md)

## 4. TEA Fetch 파라미터

| 파라미터 | 파일:라인 | 기본값 | 설명 |
|---------|----------|--------|------|
| `TEA_FETCH_WIDTH` | `core.param.def:380` | 2 | TEA fetch stage의 cycle당 fetch 폭 |
| `MAX_CHAIN_LENGTH` | `dependency_chain_cache.h:15` | 64 | 단일 chain의 최대 op 수 |
| `DEPENDENCY_CHAIN_CACHE_SIZE` | `dependency_chain_cache.h:12` | 1024 | Dep chain cache 엔트리 수 |
| `BLOCK_CACHE_SIZE` | `dependency_chain_cache.h:13` | 1024 | Block cache 엔트리 수 |

**논문과의 차이**: 논문은 TEA Fetch가 8-wide이지만 현재 기본값은 2.
전체 chain을 한번에 fetch하므로 폭이 작아도 latency 차이만 있음 (cycle 수 = chain_length / TEA_FETCH_WIDTH).

## 6. 알려진 제한사항

1. **단일 H2P만 fetch 가능**: `active_chain`이 하나의 `Dependency_Chain_Cache_Entry*`만 보유.
   TEA가 active이면 새 trigger가 거부됨 (`tea_thread.c:110` → `TEA_TRIGGER_SKIP_ACTIVE`).

2. **Block Cache 미활용**: BW Walk이 Block Cache도 채우지만 TEA Fetch는 사용하지 않음.
   방안 A에서는 Block Cache가 통계 목적/디버그용으로만 존재.

3. **TEA_FETCH_WIDTH 기본값 작음**: 논문 8-wide 대비 기본값 2. Chain이 긴 경우
   (예: 30 ops) fetch에 15 cycles 소요. 논문 방식에서는 4 cycles.

4. **BW Walk 트리거 미구현** (작업 A): `fill_buffer_add()`에서 `bw_engines->state = BW_WALKING`을
   설정하는 코드가 없어서 `dependency_chain_caches`가 비어 있음 → TEA가 활성화되지 않음.
